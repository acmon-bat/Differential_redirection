# Review of Plaster v0.1: Validation Pass (November 2026)

**Scope:** core scoring, extension collector, network restrictions, personal-information guidance and README accuracy.
**Method:** code reading, followed by **reproducible probes** for each suspected issue. A fix was made only for a demonstrated problem. Each fix has a regression test, and where the issue was behavioural, a **mutation check** shows the test fails with the old code.
**Outcome:** 7 scoring/guidance findings and 2 collector findings fixed. Methodology bumped 0.1.0 → 0.2.0. No new features added.

### Collector (`apps/extension/src/content/collector.ts`)

| ID | Severity | Finding (verified in Chromium) | Fix | Test |
|---|---|---|---|---|
| C1 | **Medium** | On privacy-policy pages, `document.body.innerText` **includes text typed into `contenteditable` regions**. Only claim flags left the collector, but user-typed text could change them, a narrow breach of "never read what users type". | Policy text is read from page-authored text nodes only, skipping `contenteditable`, form controls, scripts and templates | Integration: *typed text cannot influence policy claims*. **Fails with the old code** (mutation-checked) |
| C2 | Low | Label `textContent` included `<option>` text, e.g. "Visa ending 4242 (saved)". It was used only for classification and never retained, but it was unnecessary page content. | The same page-authored-text walker is used for labels | Covered by unit and static tests; not externally observable |

**Verified not to be an issue:** label `textContent` and `innerText` do **not** include values typed into `<input>` or `<textarea>`. Resource Timing full URLs are reduced to hosts inside the collector before anything is returned.

### Network restrictions

| ID | Finding | Action |
|---|---|---|
| N1 | The extension CSP covers **extension pages only**. The content-script collector is not CSP-protected, and the static scan only looked for direct network APIs (`fetch`, XHR and so on). An `img.src = …` pixel would have passed. | Added a static test banning indirect request sinks (resource elements, URL-bearing property and attribute assignment, navigation, workers, dynamic import). **Mutation-checked:** a tracking-pixel snippet fails it. |
| N2 | The zero-egress integration test covered only the normal page. The policy path reads page text and was untested for egress. | Added a zero-egress test for the policy-page path |
| N3 | The footer said "Plaster sent nothing over the network", which reads as a measurement | Reworded: "Plaster contains no network code and stores nothing" (true by construction and tested) |

**How the tests tell traffic sources apart:**

| Source | How it is observed | Treatment |
|---|---|---|
| Plaster popup (extension page) | Playwright `request` events on the popup page | Must be zero. The CSP also blocks it. |
| Plaster collector (content script) | Appears as requests **from the tab**, since content-script fetches carry the page's context | Must be zero during the assessment window. Fixtures are static pages, so any request then is attributable to Plaster. |
| Website traffic | Tab requests **before** the assessment window (the page settles to network-idle first) | Excluded by timing |
| Browser traffic (e.g. `accounts.google.com`) | Visible only at the proxy as HTTPS CONNECT | Excluded by host pattern (Google-owned hosts on :443) |

**Residual blind spot:** the proxy-level exclusion of Google hosts means a hypothetical exfiltration to `*.google.com` would not be caught *by that layer*. It would still be caught by the tab and popup listeners and by the static scans, and there is no background service worker (enforced by manifest test). On a live, dynamic website the tab listener would also see the site's own polling, so the timing method only works on static fixtures.

## 2. Residual issues (not fixed; need decision or future work)

1. **Provisional "A (100)" from partial evidence.** A clean site seen through `activeTab` scores 100 with medium confidence. This is consistent with "unknown is neutral" and is now visibly flagged, but a perfect number on partial evidence may still over-reassure. Options: cap the score while any category is `limitedEvidence`, or display a range. **Needs owner decision.**
2. **The policy-page heuristic** also matches pages such as `/account/privacy` settings pages. Only page-authored text is read and only flags kept (Q-5).
3. **Partial pass scores.** "None observed" under partial visibility scores 1.0 (with reduced reliability). A conservative alternative is to cap such passes, e.g. at 0.8.
4. **The weights remain uncalibrated,** and nothing has been evaluated on live websites.
5. **`navigator.sendBeacon` returns success even when blocked;** tests already assert on real traffic.

## 4. Day 2 release review

**Scope:** methodology against its documentation, privacy and security properties, documentation consistency, and release hygiene. **No new features.**

### 4.1 Scoring findings (methodology 0.2.0 → 0.3.0)

| ID | Severity | Finding (reproduced by probe) | Fix | Test |
|---|---|---|---|---|
| R8 | **High** | **Unknown evidence improved the result.** A tracker-heavy site graded **C (65)** with full evidence became **A (91)**, provisional, when third-party requests were unobservable. The 50% coverage gate let a 45%-weight blind spot through. | A grade is shown only if ≥ 75% of applicable category weight is scored and **tracking** is scored | `REVIEW R8` ×2, including a property test that removing any signal never improves the presented grade or status |
| R9 | Low | When advertising triggered the data-collection check, its explanation said "advertising" but linked *session-replay* evidence | Links the triggering category's evidence and names the domains | `REVIEW R9` |
| R10 | Low | A capped score (e.g. 39) looked like a computed score | `scoreCapped` flag; UI and CLI show "(capped)" | `REVIEW R10` |
| R11 | Low | Guidance said date of birth and government ID are "commonly hashed for ad matching". That's established for email and phone only. | Ad-matching rule limited to email and phone | `REVIEW R11` |

**Design tension (documented, not "fixed"):** a single score can't be both **neutral** about unknowns and **guaranteed never to rise** when evidence is missing. 0.3.0 keeps neutrality, protects the *presented grade and confidence*, and documents the residual numeric shift (fixtures: up to +4 within the same grade) in `scoring-methodology.md` §1.6. Invariant I-8's wording overstated this. It was reworded with owner approval on 2026-11-25 (Q-6).

**Documentation vs implementation:** the methodology document was restructured. Part 1 is 0.3.0 as implemented and authoritative; Part 2 is the original design, marked historical, with a divergence table (§1.10). One false claim was removed: `roadmap.md` said tests "prove that unknown never raises a score".

### 4.2 Privacy and security properties: assurance level

| Property | Level | Evidence |
|---|---|---|
| Form values and typed text are not collected | **Tested** | Integration: password, email and search typed into a real page; a DP claim typed into `contenteditable` and a textarea. None appears or affects the output (mutation-checked). Static: no `.value`, `FormData` or input listeners. |
| Passwords and payment details are not collected | **Tested** | Same tests; payment fields are classified by `autocomplete` only |
| Browsing history is not stored | **Tested** | Static: no storage APIs; manifest has no `storage` permission |
| Browsing history is not transmitted | **Tested** | Zero-egress integration tests (normal and policy paths); the CSP blocks fetch, image and beacon from the popup |
| No extension-initiated requests during assessment | **Tested** (fixtures) | Tab, popup and proxy observation; mutation-checked. Proxy-layer exclusion of Google hosts is a documented blind spot. |
| Only intended permissions | **Tested** | Static (source manifest), integration (installed test build), plus a Day 2 scripted check of the **production** build loaded in Chromium |
| No test hooks in production | **Tested** | Static: bundle scan; production manifest equals the source manifest. Day 2: hook absent at runtime. |
| No unsafe HTML handling | **Tested** | Static: no HTML sinks in source **and, new on Day 2, in the production bundles**. Rendering uses `textContent` only. |
| No indirect network sinks in collector or popup | **Tested** | Static sink scan, mutation-checked |
| Page scripts cannot tamper with the collector | **Documented assumption** | Chromium isolated-world semantics |
| `activeTab` grants access only after a user gesture, to the main frame | **Documented assumption** | Chromium documentation; the test build substitutes a host permission |
| Behaviour on live websites, other Chromium versions, Firefox | **Unverified** | Not tested |

**New observations recorded as limitations (not fixed, since that would be new work):**
- Forms inside shadow DOM are not inspected, so sensitive fields there are under-reported.
- Full hostnames, including per-user subdomains, appear in the in-popup snapshot. They are never stored or sent.
